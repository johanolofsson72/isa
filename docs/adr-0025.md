# ADR-0025: Idempotenta workflows & återkörning

## Status
Accepted — 2025-09-11

## Kontext
ADR-0004 slog fast att utskick och importer ska vara idempotenta.  
I praktiken behöver detta implementeras konsekvent i **Quartz-jobb, notifieringar och dokumentflöden**.  
Issues beskriver problem med dubbletter i notifieringar, misslyckade imports och behov av Dead-letter queues (DLQ).

## Beslut
- **Idempotensnyckel**  
  - Alla workflows och notifieringar använder en unik `externalIdempotencyKey`.  
  - Nyckeln loggas i `JobHistory` och kontrolleras innan exekvering.  

- **Retry-mekanismer**  
  - Exponential backoff används för alla externa API-anrop (Fortnox, Twilio, Verified).  
  - Max retry-count definieras per integration (ex. 5 försök).  
  - Misslyckade jobb flaggas med `FAILED` i `ExecutionResults`.  

- **Dead-letter Queue (DLQ)**  
  - Permanenta fel skickas till DLQ.  
  - DLQ är åtkomlig i WebChat för manuell hantering.  
  - Admin/Systemansvarig kan återköra ett DLQ-jobb direkt från UI.  

- **Quartz-integration**  
  - Alla Quartz-jobb använder `WorkflowExecutionContext` med idempotensnyckel.  
  - `QuartzWorkflowService` ansvarar för att logga resultat.  
  - Hälsokontroller säkerställer att schemalagda jobb inte hänger sig.  

- **Notifieringar**  
  - Alla utskick (mail, SMS, Slack, WhatsApp) sparas i `NotificationLog` med idempotensnyckel.  
  - Dubbelutsändningar blockeras automatiskt.  

## Konsekvenser
+ Säkerhet mot dubbletter i alla arbetsflöden.  
+ Möjlighet att manuellt återköra misslyckade flöden utan datakorruption.  
+ Konsistent felhantering via DLQ.  
- Kräver extra kod och logik för idempotenshantering.  
- Viss komplexitet i att generera nycklar på ett korrekt sätt.
